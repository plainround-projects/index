# Repository conventions for Plainround reference projects

Every project lesson in the Plainround app (`/Users/sumitsrivastava/Code/ds-explainer/data-structure-explainer/src/content/tracks/<track>/<nn>-project-<slug>.md`) gets one repository here, named `<track>-<slug>`, that is the real build of what the lesson asks for: it runs, its tests pass, and its README lets a reader reproduce every "Done when" line of the lesson. Each repository is its own git repository (`git init` inside it, no nesting under this folder's git), so it can be pushed to GitHub on its own later.

## What every repository holds

- `README.md`, detailed: the one-sentence purpose; the lesson it realizes (path and title) and the hours the lesson plans; prerequisites with versions (runtime, Docker, cloud account or none); setup, run, test and stop commands that work as written on a Mac; the "Done when" checklist from the lesson with the command or observation that proves each line; the stretch goals and whether they are built; what is simplified for teaching; the license line.
- `ARCHITECTURE.md`: the components and what each owns, the data flow as a Mermaid diagram plus a numbered walk-through of one request or run, the decisions and their trade-offs (why this queue, this schema, this timeout), the failure modes the lesson teaches and how the code shows them, the limits of the teaching build against a production one, and how to extend it.
- Source under `src/` (or the language's convention), tests under `tests/` (or the language's convention), one command to run them, and a `Makefile` or package scripts so `make run`, `make test` (or `npm run`, `./mvnw`) are the only commands a reader needs.
- `sql/` whenever the project touches a database (Sumit, 2026-10-27: "add the sql scripts as well in the repo, ddl, dml etc."): numbered files that run in order with one command (`make db` or a script named in the README), `001_schema.sql` (DDL: tables, keys, indexes, constraints, comments), `002_seed.sql` (DML: the data the lesson's examples use, enough rows for the lesson's measurements), `003_queries.sql` (the queries the lesson runs, each with a one-line comment on what it shows), `migrations/` for every schema change the lesson makes in steps (expand and contract where the lesson teaches it), and `explain/` for the query-tuning projects (each query's `EXPLAIN (ANALYZE, BUFFERS)` before and after, as `.sql` plus the captured plan as `.txt`); the same for a document or key-value store in its own script language (Cypher, Redis commands, the vendor's CLI) under the same folder.
- `tech/`: one beginner-level file per technology the repository uses, plus `tech/README.md` as its index (format in the "Technology notes" section below).
- `.github/workflows/ci.yml` that runs the tests on push; `.gitignore` for the stack; `.env.example` with every variable and no secret; `LICENSE` (MIT, Sumit Srivastava, the year); `docker-compose.yml` when the lesson runs a service in a container.
- No company names in examples, no secrets, US English, no "Section" symbol in prose. The owner is Sumit Srivastava; the author line in the README names him.

## Production grade (rule set by Sumit, 2026-10-27: "production grade code quality with best possible designs applied")

A teaching build is still a production build. Every repository meets this bar, and the README's "What is simplified for teaching" names only what the lesson scopes out (a single node instead of a cluster, a stub payment provider), never a shortcut in the code.

- **Design.** A clear layering: domain logic separated from transport (HTTP, Kafka, CLI) and from infrastructure (database, broker, files), ports and adapters where the lesson's system has more than one boundary; small modules with one responsibility each; dependency inversion for anything a test needs to replace; immutable value objects; named errors; no global mutable state; configuration from the environment with validated defaults (twelve-factor), never from hard-coded values. The ARCHITECTURE.md names the pattern used and why it fits this project.
- **Code.** The language's current stable version and its standard tooling: typed code (TypeScript strict, Python with type hints and `mypy` or `pyright`, Java records and sealed types where they fit), a formatter and a linter configured in the repository and run in CI, docstrings or Javadoc on the public surface, no dead code, no TODOs left in.
- **Correctness.** Unit tests for the domain, integration tests against the real dependency in a container, one end-to-end run of the lesson's scenario, test names that read as behavior; coverage reported, with the domain at or near full coverage; idempotent operations where a retry is possible; input validation at every boundary; time and randomness injected so tests are deterministic.
- **Operability.** Structured logging with levels and no secrets in logs; a health endpoint or health command; graceful shutdown (signals handled, in-flight work finished, connections closed); timeouts and retries with backoff on every network call; metrics or counters where the lesson measures something; a `Dockerfile` with a non-root user and a pinned base image for anything that serves traffic.
- **Security.** Secrets only from the environment; least privilege in every infrastructure definition; dependencies pinned with a lock file and checked by the CI's audit step; no credentials, tokens or personal data in fixtures.
- **Delivery.** CI runs format, lint, type check, tests and the audit on every push; a `make` or script target per step; semantic commit messages; a CHANGELOG.md started at the first version; the README's commands verified by the fresh-clone test.

## Project structure (rule set by Sumit, 2026-10-27: "and project structure as well")

Every repository follows the standard layout of its stack, and its README carries a "Project structure" section: the tree, one line per folder saying what lives there and what may depend on what. The layers are folders, so the dependency rule (domain depends on nothing; application depends on domain; infrastructure and interfaces depend on both; nothing depends on interfaces) is visible in the tree and enforced by the linter or a test where the stack allows (an import-boundary rule, an ArchUnit test, a `pyproject` import-linter).

- **Python:** `pyproject.toml` (one tool config file; `uv` or `pip` lock), `src/<package>/` with `domain/`, `application/`, `infrastructure/`, `interfaces/` (CLI, HTTP, consumers), `tests/unit/`, `tests/integration/`, `tests/e2e/`, `scripts/`, `sql/` where there is a database, `docker-compose.yml`, `Dockerfile`, `Makefile`.
- **Java:** Maven or Gradle standard layout with the wrapper checked in, a module or package per layer (`domain`, `application`, `infrastructure`, `interfaces`), `src/test/java` mirrored by package, ArchUnit for the dependency rule, `src/main/resources/db/migration` for SQL when Flyway fits the lesson, `docker-compose.yml`, `Dockerfile` with a multi-stage build.
- **TypeScript or Node:** `package.json` with a lock file, `src/` with the same four layers, `tests/` by level, `tsconfig.json` strict, ESLint with an import-boundary rule, `docker-compose.yml`, `Dockerfile`.
- **Go:** `cmd/<binary>/`, `internal/` with the layers, `pkg/` only for code meant to be imported by others, `go.mod`, table-driven tests next to the code, `docker-compose.yml`, `Dockerfile`.
- **Infrastructure as code:** `infra/` with `modules/` (one per reusable piece) and `environments/<name>/` (the composition per environment with its variables file), `terraform fmt` and `validate` in CI, a `README` per module.
- **Kubernetes or platform repositories:** `manifests/` or `charts/` with `base/` and `overlays/<env>/`, `scripts/` for the lesson's runbook commands, `tests/` with the conformance or smoke checks the lesson names.
- **Pipelines:** `.github/workflows/`, `Jenkinsfile` or the tool's file at the root, `pipeline/` for reusable steps, `tests/` for the pipeline's own tests where the tool allows (for example `act` or a unit-tested script).

Never commit build artifacts or local state: `*.egg-info`, `__pycache__`, `.venv`, `node_modules`, `target`, `dist`, `logs/`, `.pytest_cache`, coverage output; the `.gitignore` covers them and `git status` after the final commit shows nothing untracked. Lock files are committed.

Common to all: `README.md`, `ARCHITECTURE.md`, `CHANGELOG.md`, `LICENSE`, `.gitignore`, `.env.example`, `.editorconfig`, `Makefile` (or the stack's script runner) with `up`, `run`, `test`, `lint`, `down`; `docs/` for anything longer (decision records as `docs/adr/NNNN-title.md` when a project makes a real choice); no file at the root that the stack does not need.

## Cloud projects

A project whose lesson deploys to AWS, Azure or Google Cloud holds its infrastructure as code (Terraform unless the lesson names another tool), validated locally (`terraform init -backend=false && terraform validate` and a `plan` against a documented variables file where no credentials are needed), the application code with its own local tests, and README deploy steps with the exact commands, the cost it incurs per the lesson's register, and the teardown. Nothing is deployed from here; the owner deploys when the account exists.

## Technology notes, the `tech/` folder (rule set by Sumit, 2026-10-28: "add a tech related folder in each repo and create a dedicated file for each technology used in that repo, even the bash/shell script level, and explain the low level details, good enough to understand what work has been done in that repo, considering the learner is complete naive and has no familiarity of those technologies at all")

Every repository has a `tech/` folder. It teaches each technology the repository uses, from zero, through this repository's own files.

**Which technologies get a file.** One file per technology that appears in the repository: the language and its version (Python 3.12, Java 21, Go 1.23, TypeScript), each framework and each library that the code imports or the manifest pins (FastAPI, Spring Boot, SQLAlchemy, Testcontainers, pytest, JUnit), each tool (Bash, Make, Docker, Docker Compose, kind or k3d, kubectl, Helm, Terraform, GitHub Actions, uv, ruff, mypy, import-linter), each service it runs (PostgreSQL, Kafka, Redis, Prometheus, Grafana, Keycloak), and each file format it relies on (YAML, TOML, Dockerfile syntax, SQL). The test: if a file of that kind, an import, or a pinned dependency exists in the repository, the technology gets a file. Expect eight to twenty files. Name them `tech/<technology>.md` in lower case with hyphens (`tech/bash.md`, `tech/docker-compose.md`, `tech/postgresql.md`).

**`tech/README.md`** lists every file with a one-line role ("Bash: the scripts under `scripts/` that start and stop the stack"), says in which order to read them (the language first, then the build tool, then the runtime pieces, then the tests), and names the three files to read if the learner has ten minutes.

**Format of each `tech/<technology>.md`**, in this order, with these headings:

1. **What it is.** Two or three plain sentences. What problem it solves, and what kind of thing it is (a language, a library, a command-line tool, a server, a file format). Define every term the first time it appears.
2. **Why this repository uses it.** Tie it to the lesson's goal in one short paragraph.
3. **Where it appears.** A table: file path, what that file does with the technology.
4. **How it works underneath.** The mental model a beginner needs: what runs as a process, what is a file on disk, what goes over the network, what lives in memory, what happens in which order. Short sentences. One idea per sentence.
5. **Walkthrough of this repository's use.** The heart of the file. Go through this repository's own code, scripts and configuration for this technology and explain every non-trivial line, flag, key or instruction. For a shell script: each command, each flag, each pipe, `set -euo pipefail`, exit codes, traps, quoting. For a Dockerfile: each instruction and why it is in that order. For a Makefile: each target and its dependencies. For a compose file or a Kubernetes manifest: each key. For SQL: each statement. For a language: the features this code uses (type hints, dataclasses, async, generics, records, streams), explained where they appear. Quote the lines in fenced code blocks, then explain them. Nothing is "obvious".
6. **Try it yourself.** Three to five commands the learner can run in this repository to watch the technology do its work, each with the expected output or what to look for.
7. **Mistakes people make.** The common errors with this technology and how this repository avoids them.
8. **Check yourself.** Five questions with answers that a reader of this file can answer.
9. **Further reading.** Official documentation links only, with the version this repository pins.

**Rules (Sumit, 2026-10-28: "make sure the language is simple and covers the explanation very well, leaving no topic, assuming the learner would already be knowing" and "no short-cuts please").** Simple words, short sentences, no jargon left undefined. Assume the reader has never seen a terminal, a container, a package manager or this language: when the walkthrough meets a concept (a process, a port, an environment variable, a file descriptor, a virtual environment, a JSON object, a thread, a transaction, a TLS certificate), explain it right there in two or three sentences before going on. Leave no topic out because it "is basic"; the test is that a reader with zero background can follow every line of this repository with these notes alone. No shortcuts: no "see the docs for details", no "and so on", no summarizing ten lines as "boilerplate". Every file, script, configuration key and command in the repository that uses the technology is covered. If a file is long, the walkthrough is long. Everything stated must be true for the version this repository pins; verify against the official documentation before writing it. No padding: as long as needed to make this repository fully readable without outside help, and not longer. The notes describe what is actually in the repository, so write them after the code is final and update them when the code changes. **Measured bar.** `python3 tools/techcov.py report.json <repo-folder>` prints, per repository, the share of non-blank, non-comment lines of every tracked source, script and configuration file that is quoted in `tech/*.md`, and the three least-covered files. A repository's notes are complete at 95 percent or more; the sessions that wrote line-by-line walkthroughs reach 99 percent. Run it before reporting. The index `README.md` and `projects.json` carry `tech: <n files>` once the folder is complete and the bar is met.

## Shared machine (rule from 2026-10-27, after six parallel `kind create cluster` runs timed out on a load average above 140)

- Only one `kind create cluster` runs on this machine at a time. A repository that needs a cluster brings it up through `scripts/kind-up.sh`, which takes the lock `mkdir /tmp/plainround-kind-create.lock`, writes its PID to `<lock>/pid`, retries every 30 s while the mkdir fails (a lock whose PID is dead is stale and may be removed), and removes the lock when `kind create` finishes or fails.
- One cluster per repository at a time; single control-plane node unless the lesson needs workers; `scripts/kind-down.sh` deletes it, and the README's verification ends with that call.
- Compose stacks come down (`docker compose down -v`) at the end of every verification; nothing stays up between runs.

## Verification before a repository is called done

1. Fresh clone test: in a temporary folder, follow the README from the top; every command works.
2. Tests pass with the one command; CI file mirrors it.
3. Every "Done when" line of the lesson is demonstrated and the README says how.
4. The lesson's diagram and the repository's ARCHITECTURE.md agree on component names.
